Holding an HTTP request until a human says yes

Shane · October 2026 · notes from building Friction in Rust

Friction is a local proxy that sits between AI agents and the internet. When an agent tries to pay for something or send an API key to the wrong place, the request stops and waits for me to click allow or block. Building that in Rust meant solving a few problems I hadn't dealt with before. These are the ones worth writing down.

The stack is hyper 1 for HTTP, tokio-rustls for TLS, rcgen for certificates, and Tauri for the menu bar UI. Agents reach the proxy through the usual HTTPS_PROXY variable, which friction run -- python agent.py sets for one process along with the CA bundle variables that Python, Node, curl and git each read.

1. Being every server at once

To read an HTTPS request, the proxy has to terminate TLS itself. An agent sends CONNECT api.stripe.com:443, the proxy answers 200, and from then on the agent expects to be talking TLS to Stripe. So the proxy needs a certificate for api.stripe.com that the agent will accept.

On first launch Friction generates a root CA with rcgen and writes the key with 0600 permissions. For each host it mints a leaf certificate signed by that CA, builds a rustls ServerConfig around it, and caches the config by host name:

pub fn server_config_for(&self, host: &str) -> Result<Arc<ServerConfig>, BoxErr> {
    if let Some(cfg) = self.cache.lock().unwrap().get(host) {
        return Ok(cfg.clone());
    }
    let mut params = CertificateParams::new(vec![host.to_string()])?;
    params.is_ca = IsCa::NoCa;
    params.extended_key_usages = vec![ExtendedKeyUsagePurpose::ServerAuth];
    params.use_authority_key_identifier_extension = true;
    // ...validity window, random serial...
    let leaf_key = KeyPair::generate()?;
    let leaf = params.signed_by(&leaf_key, &self.issuer, &self.issuer_key)?;

    let mut cfg = ServerConfig::builder()
        .with_no_client_auth()
        .with_single_cert(vec![leaf.der().clone()], key_der(&leaf_key))?;
    cfg.alpn_protocols = vec![b"http/1.1".to_vec()];
    // cache and return
}

Two details mattered. The leaf carries an authority key identifier, which some TLS clients use to find the issuing certificate when they build the chain back to the root. And ALPN is pinned to http/1.1, so clients don't negotiate HTTP/2 with a proxy that only speaks HTTP/1.1 on the inner connection.

After the 200, the CONNECT request is upgraded and the raw stream is handed to a TLS acceptor. The decrypted stream then gets its own hyper connection, served by the same request handler as plain HTTP, with the target host carried along:

tokio::spawn(async move {
    let upgraded = hyper::upgrade::on(req).await?;
    let tls = TlsAcceptor::from(server_cfg).accept(TokioIo::new(upgraded)).await?;
    let target = Target { https: true, host, port, agent };
    let service = service_fn(move |r| handle_request(app.clone(), state.clone(), Some(target.clone()), r));
    http1::Builder::new().serve_connection(TokioIo::new(tls), service).await
});

That reuse was the best decision in the codebase. Every rule, from payment detection to spend metering, is written once and applies to HTTP and HTTPS the same way.

2. Parking a request

When a request needs approval, the handler can't return. It has to wait, possibly for a minute, while a notification goes out and the UI shows what the agent is sending. A tokio::sync::oneshot channel is the natural fit: the sender goes into a map of pending requests that the UI's "allow" and "block" commands look up by id, and the handler awaits the receiver with a timeout.

let (tx, rx) = oneshot::channel();
state.pending.lock().unwrap().insert(id.clone(), Pending { tx, payload: payload.clone() });
let mut guard = HoldGuard { armed: true, /* what to log if we never get an answer */ };

let decision = tokio::time::timeout(Duration::from_secs(120), rx).await;
guard.armed = false;
match decision {
    Ok(Ok(Decision::Approve)) => { /* forward upstream */ }
    Ok(Ok(Decision::Reject)) => return Ok(text(403, "Friction: transaction was rejected by the user.")),
    _ => { /* timed out: blocked */ }
}

The interesting case is the one that isn't in the match. If the agent gives up and closes the connection, hyper drops the handler's future. No timeout fires and no branch runs; the code after the .await simply never executes. Without care, the request would sit in the UI forever, waiting for a decision no one can act on.

The fix is a guard whose Drop does the cleanup. It's armed while waiting and disarmed once a decision comes back normally. If the future is dropped while the guard is still armed, the drop removes the pending entry, tells the UI it expired, and records it as blocked with "Agent disconnected":

impl Drop for HoldGuard {
    fn drop(&mut self) {
        if !self.armed { return; }
        let was_pending = self.state.pending.lock().unwrap().remove(&self.payload.id).is_some();
        if !was_pending { return; }
        let _ = self.app.emit("intercept:expired", &self.payload.id);
        // ...write the audit entry...
    }
}

Cancellation in async Rust is easy to forget because it is silent. Treating "my future might just stop here" as a normal path, and putting the cleanup in a destructor, made the whole hold flow robust.

3. Watching a stream without holding it up

Friction meters what agents spend on AI APIs by reading the token counts in each response. Many of those responses are server-sent event streams that run for a minute or more, and buffering them would break the agent's streaming. The counts are usually at the start (Anthropic's message_start) or the end (OpenAI's final usage chunk) of the stream.

So the response body is wrapped in a small http_body::Body that passes every frame straight through while keeping a copy of the first and last 256 KB:

impl hyper::body::Body for TapBody {
    type Data = Bytes;
    type Error = hyper::Error;

    fn poll_frame(self: Pin<&mut Self>, cx: &mut Context<'_>)
        -> Poll<Option<Result<Frame<Bytes>, hyper::Error>>>>
    {
        let this = self.get_mut();
        match this.inner.as_mut().poll_frame(cx) {
            Poll::Ready(Some(Ok(frame))) => {
                if let Some(d) = frame.data_ref() { this.capture(d); }
                Poll::Ready(Some(Ok(frame)))
            }
            Poll::Ready(None) => { this.finish(true); Poll::Ready(None) }
            other => other,  // Pending, or an error (which also calls finish(false))
        }
    }
}

impl Drop for TapBody {
    fn drop(&mut self) { self.finish(false); }
}

capture fills the head up to the limit, then appends to a tail that it trims from the front, so memory stays bounded however long the stream runs. finish runs exactly once (it takes a FnOnce out of an Option), either at the end of the stream or from Drop if the client hangs up, and hands the captured bytes to the code that parses usage and prices the call.

One shortcut made this practical: for AI API hosts, the proxy rewrites the request's Accept-Encoding to identity. Responses from those APIs come back uncompressed, so the tap can parse them as they are. It costs a little bandwidth and saves a streaming decompressor.

4. Reading money out of a request

Payment detection is deliberately boring: a table of documented endpoints, matched on method, host and path, with a parser per processor for the amount. The traps were in the units. Stripe, Square and Adyen send amounts in the currency's minor unit, so amount=27900 with currency=usd is $279.00. But some currencies have no minor unit, and for those the number is already whole:

const ZERO_DECIMAL: &[&str] =
    &["bif", "clp", "djf", "gnf", "jpy", "kmf", "krw", "mga", "pyg", "rwf", "ugx", "vnd", "vuv", "xaf", "xof", "xpf"];

fn from_minor(value: f64, currency: &str) -> f64 {
    if ZERO_DECIMAL.contains(&currency.to_ascii_lowercase().as_str()) { value } else { value / 100.0 }
}

Getting this wrong would show a ¥5,000 charge as ¥50, which is exactly the kind of number a person approves without thinking. PayPal and Coinbase send decimal strings instead, so they skip the conversion.

5. Config that can't fail open

Rules live in ~/.friction/rules.toml, which people edit by hand while agents are running. A background task checks the file's modification time every second and reparses when it changes. A parse error never replaces the loaded rules: Friction keeps enforcing the last good version and shows the error with its line number until the file is fixed. For a tool whose job is to stop things, a typo shouldn't be able to turn the protection off.

What's next

Friction only sees traffic from programs that use its proxy. That covers most agent tooling, since Python, Node, curl and git all honor the proxy and CA variables, but code that opens its own sockets goes around it. Closing that gap means a macOS network extension, which is the next big piece. HTTP/2 between agent and proxy is the other.

The code is MIT licensed and on GitHub. I'd especially like feedback on the proxy internals; I'm sure parts of this can be done better.
